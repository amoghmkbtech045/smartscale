The problem

Serverless platforms start new instances only after existing ones get busy. A new instance needs seconds to boot (a cold start), so users queue during every surge. Reactive scaling also cannot tell a flash sale from an attack, so it pays for fake traffic as well.

The solution pipeline

  1. Telemetry: every 0.5 s step it measures request rate, endpoint entropy, share of the busiest endpoint and payload variation.
  2. Anomaly detection: an Isolation Forest trained on normal traffic (including flash sales) scores each step. A step is treated as an attack only if it is a statistical outlier and traffic is concentrated on one endpoint.
  3. Targeted rate limiting: repeated identical payloads on the attacked endpoint are limited. Varied legitimate requests still pass.
  4. Forecasting: a Gradient Boosting model predicts the clean request rate four seconds ahead from recent lags, trend and variance.
  5. Pre-warming: instances needed for the forecast start immediately, so they are ready when demand lands.

The baseline

A Kubernetes HPA-style controller: it scales when utilisation exceeds 65 percent, evaluates every 2 steps, and waits 12 steps before scaling down. It reacts to all traffic, genuine or not.

The runtime

Each instance is a real worker thread with a cold-start delay, pulling from a request queue. Latency is timed per request. The two systems run at the same time on the same pre-generated trace, so differences come from the scaling logic only.

Limitations

The runtime is emulated on one machine, not a real Knative or Lambda cluster. Models are trained on synthetic normal traffic. Cost uses an illustrative price per instance-second. Time is scaled down (a 3 s cold start stands in for a real one).

What each number means

  • Average, p50, p95, p99 latency: response time of legitimate requests, from arrival to completion. p95 means 95% of users were faster.
  • Requests over SLA: share of legitimate requests slower than your latency target.
  • Cost: billed instance-seconds multiplied by an illustrative price. Booting instances are billed.
  • Instance-seconds wasted on attack: extra instances kept running above the minimum while an attack was in progress.
  • Attack requests blocked: share of attack requests stopped by the filter.
  • Legit requests wrongly blocked: real users caught by the filter. Lower is better.
  • Forecast error (WAPE): total absolute forecast error divided by total actual load. Lower is better; sudden jumps are hard to predict.
SmartScale runs entirely on this computer. Results vary slightly between runs because real threads and timers are involved.
